## 3. 关键设计

详细写清所有「关键 / 亮点 / 难点」设计；与 `tech.yaml` → `keyDesigns` 一一对应。开发 Agent 实现时须落实每条的 `mustFollow` 要点，且不得踩 `pitfalls`。

### 3.1 判定原则（什么算关键设计）

命中 **任一条** 即应单独成条写入本节（不要塞进一笔带过的概述里）：

| 判定 | 含义 | 典型例子 |
| --- | --- | --- |
| **关键（cornerstone）** | 不做对则整切片验收或主路径失败；或其它模块/后续 feature 必须依赖的契约 | 幂等键、状态机跃迁、跨 feature 接口、权限边界 |
| **亮点（highlight）** | 相对常规实现有意选择的更优路径，或可复用的抽象，值得审阅确认 | 统一错误模型、可插拔策略、显著降复杂度的分层 |
| **难点（difficulty）** | 并发/时序/失败恢复/性能功耗/兼容性上容易做错，或历史坑多 | 双写窗口、取消与重入、大图滑动与内存、厂商 API 差异 |

**不必写成关键设计**（可留在概述或普通选型里）：纯命名调整、机械搬家、无新约束的样板代码、已有模式的简单套用且无新不变量。

每条关键设计须写清：**问题 → 决策 → 为何算关键/亮点/难点 → 核心方案叙述（链路闭环）→ 对 AI/人的约束 → 关联图与 A\***。  
（叙述质量：主路径闭环、关键技术点露面、关键环节可落地、与图互证。详版可另存 `key-designs/`，模板见 `templates/design/key-design-kd.md`。）
