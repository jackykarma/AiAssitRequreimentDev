插件与工作流新手指南

对主控说出需求，Agent 按角色写出规格、过门禁、推进交付。 本文覆盖安装、30 分钟上手、门禁地图，以及选型优劣势与进阶要点。

30 分钟上手 先看安装

1. 它是什么

AiAssitRequreimentDev 是「对话编排 + 规格门禁」的多智能体流水线。 合同落在 features/<id>/；你主要跟主控说话，文档与 check 由 Agent 代跑。

REQ

需求

业务问题 / 史诗。大需求可建 requirements/REQ-…/（需求级 PRD + split.yaml）。

FEAT

feature

可独立过 G4 的交付切片。一条需求 → 1..N 个 feature；产物共仓在 features/<id>/。

TASK

task

feature 内实现单元。只在该 feature 的 G2T 之后由主控写入 tasks.yaml，不是拆需求。

推荐 小需求直开 feature

  • 路径短，边界清晰时最快落地
  • 切片 PRD 可兼任需求级说明
  • 适合「一句话能说清验收」的改动

慎用直开 大需求 / 多批次

  • 范围一变难收，易变成半成品堆
  • 应先需求级 PRD + split.yaml 再 init
  • 禁止批量空建 feature 再补故事

2. 安装与准备

Python ≥ 3.11。团队插件源在本仓库 plugins/aiassitrequreimentdev/；业务仓读插件 references/ 即可，完整 modus/ 可选。

Cursor
  1. Customize → 从本 Git / 团队 marketplace 安装 aiassitrequreimentdev
  2. 新开 Agent 会话后使用 lead 等技能
  3. 本仓开发时同步技能：
python scripts/sync_plugin_skills.py
Codex
  1. 将本仓库加入 Codex marketplace（.agents/plugins/marketplace.json）
  2. /plugins 安装 aiassitrequreimentdev 后新开会话
  3. CLI：python <plugin>/scripts/aad.py …（等价 python -m aiassitrequreimentdev）

插件 references

  • 装完即有，跨仓一致
  • 适合标准流程与门禁知识

业务仓 modus

  • 可贴业务深，需人维护
  • 易与插件漂移；改完记得同步技能
本地可编辑安装 CLI：python -m pip install -e .。marketplace 仅含插件目录时，可设 AAD_GIT_REMOTE 供懒装。

3. 30 分钟上手

默认路径：对主控说话。启用技能 aiassitrequreimentdev-lead，不要一上来自己手写门禁状态。

  1. 说出需求 例如：「做一个相册移动到其他图集的功能」。模糊时主控会走 brainstorm → grill → product。
  2. 选角色 主控在对话内弹选项（AskQuestion 或编号菜单），确认后 adopt。HTML 仅备用。
  3. 确认路径 full / light / light-auto 主控在对话内展示推荐并弹选项，确认后 path（须 pathConfirmed）。HTML 仅备用。
  4. 看共仓产物 每个 feature 的 BOARD.md 是进度板；规格、原型、tech、证据都在同一目录。

先 brainstorm / grill

  • 输入模糊时减少 G1 打回
  • 闭合旅程、异常、非目标后再冻规格
  • 代价：多一轮澄清对话

直接写 PRD

  • 输入已完整时更快
  • openQuestions 未空会卡 G1
  • 适合边界与验收已写清的小需求

小需求 CLI 等价（通常由主控代跑）：

python -m aiassitrequreimentdev start FEAT-001 --need "相册移动到其他图集"
python -m aiassitrequreimentdev check features/FEAT-001 --gate G1

4. 工作流与门禁

阶段：intake → clarify → ux → tech → plan → implement → review → verify → release → done。结构通过后再往下；G1 后 seal；交付后 board。

G0path G1产品合同 G2UX G2T技术方案 G3任务图 GRReview G4证据 GD部署清单
门禁谁写出 / 要点
G0主控：path 合法；light 的 affected 恰好一项
G1产品：prd / 原型 / spec.yaml（UJ/FR/NFR/E/A；开放问题为空）
G2交互视觉：ux.yaml + 可交互 prototype/ux/；无 UI 或 light 可 skip
G2T架构师：tech.md + tech.yaml；图用 Archify（html+svg）
G3主控写 tasks.yaml 后检查；无环、写集不交；light 仅一任务
GRReview：无未关闭 blocking、无未裁决 dispute；nit 不挡
G4测试：evidence.yaml 全覆盖且 exitCode 0
GD部署：deploy.yaml 含 environment / commands / rollback

full

  • 覆盖 UX → 部署，完整可追溯
  • 适合有 UI、多角色协作的正式切片
  • 代价：回合多、工件全

light

  • 快，适合单点改动
  • 仅一项 affected、可无完整 UX、只能一个任务
  • 复杂需求易返工，勿硬套 light

5. 角色与写出边界

角色只写自己的工件。门禁由主控代跑 check，不要手改 gates.*.accepted。

技能只写
aiassitrequreimentdev-leadstate.json、tasks.yaml、usage.yaml（经 CLI）、代跑 CLI
…-brainstorm / …-grill探索与追问；不冻正式规格 / 不写代码
…-productprd.md、prototype/index.html、spec.yaml（大需求另写需求级 PRD / split.yaml）
…-uxux.yaml、prototype/ux/
…-techtech.md + tech.yaml；图用 archify 技能
…-dev任务写集内源码
…-reviewreview.yaml
…-testevidence.yaml
…-deploydeploy.yaml

UX · ui-kit（默认）

  • 与 kit 一致，过 G2 成本低
  • 适合大多数业务界面

UX · custom

  • 视觉自由，须补 notes 与验收覆盖
  • 审查更重；非品牌强诉求时别默认 custom

6. 新手最佳实践

把流程当成「合同机」：先冻结可验收的规格，再实现；变更先记账再回退门禁。

  • 总是从 lead 起步——选角色、确认 path、派技能、代跑 CLI，避免角色越权写别人的工件。
  • 小需求别硬拆——默认少拆；能一个 feature 独立交付就不要空建多个。
  • 门禁失败先修工件——看检查器报错改 prd/spec/ux/tech，不要手改 accepted。
  • blocking 禁止进测——先修复并复审；dispute 等人裁决；nit 可后续。
  • 验收命令同源——任务验证须与 spec.acceptance[].verify 同名/同源，禁止另起总能成功的假命令。
  • 改合同先 change——产品/UX/技术/拆分变更：先 change.yaml，再回退门禁，再改文件。
  • 阶段结束记 usage——主控代跑 usage record，看板才完整。
工具页：角色选择 · 路径选择 · 架构说明见 architecture.md

7. 进阶（折叠）

维护者与大需求负责人再展开。细则以插件 references/ 为准。

大需求：init-req → split → 多 feature

顺序：需求级 PRD →（可选）整需求 Archify 草图 → 产品填 split.yaml → decision: multi 时人确认 → 主控 init 各 feature 并带 --requirement → 各切片 PRD/spec → 各自 tech（G2T）。

python -m aiassitrequreimentdev init-req REQ-001-move-album-20220305
python -m aiassitrequreimentdev init FEAT-001 --requirement REQ-001-move-album-20220305
变更级别 C0–C4
级别含义回退
C0实现细节可不回退；建议仍记账
C1技术方案合同→ G2T，重评 G3
C2UX/UI（不改 A*）→ G2
C3产品合同→ G1 重 seal；下游重做；须人确认
C4范围/拆分需求级 PRD / split；须人确认
Review / usage / 目录速查
  • Review：blocking → 回 implement 复审；dispute → 主控打断；nit → 可进 verify。
  • usage：usage record --role … --stage … --input … --output …；看板 board。
  • 目录：requirements/REQ-…/；features/<id>/ 含 state、BOARD、prd、prototype、spec、ux、tech、diagrams、tasks、review、evidence、deploy、change、usage。
